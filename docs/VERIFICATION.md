记录对 `simp.csuft.edu.cn` 实际接口的验证结论与证据。
所有结论均来自 2026-09-30 的真实抓包与请求，非推测。

> **2026-10-09 更新**：新增 §七，修正签到状态码语义。

## 一、验证方法

由于小程序使用微信 openid 静默登录（`grant_type=wxapp`），网页端无法复用其登录，
且服务端**拒绝** `grant_type=password`（仅网页端客户端 `flySource` 支持，
但与小程序客户端凭据不通用），因此采用抓包方式取得真实凭据：

1. mitmproxy 监听 `127.0.0.1:8888`，并开启系统代理
2. 把 mitmproxy CA 装入「当前用户 → 受信任的根证书颁发机构」
   —— 不做这一步，微信小程序会因证书不受信而报「网络错误」
3. 重启微信 PC 端，在小程序中进入「打卡」页
4. 捕获到真实的 `FlySource-Auth` 头（JWT）

抓包工具：`tools/capture_addon.py`、`tools/system_proxy.py`、`tools/install_ca.py`。

## 二、核心结论：签名算法

### 发现的 Bug

初版实现用**完整 URL**（含 `https://simp.csuft.edu.cn`）参与签名 —— **错误**。
抓包比对（936 种组合穷举）后确认唯一正确形式：

```
签名输入 = 相对路径(去掉 query) + "?sign="
签名     = md5(签名输入 + md5(str(ts) + token)) + "1." + base64(str(ts))
```

### 两个易错点（已固化为单元测试）

| 易错点 | 正确做法 |
|---|---|
| 用完整 URL | 必须用**相对路径**（`/api/xxx`），且**剔除 query** |
| token 加 `bearer ` 前缀 | 用**原始 token**（小程序不加前缀；网页端才加） |

### 实测证据

| 请求 | 时间戳 | 小程序签名 | 我们的签名 | 结果 |
|---|---|---|---|---|
| `getListForApp?current=1&size=10` | 1790699446853 | `5f5375a7…1.MTc5…` | 同 | ✓ 一致 |
| `getTaskByIdForApp?taskId=45f9…` | 1790699448573 | `30dd2190…1.MTc5…` | 同 | ✓ 一致 |

回归测试：`tools/test_units.py` 中的「抓包向量一致」两项。

## 五、Token 生命周期

JWT 内含 `exp` 声明，本次抓到的 token 有效期约 **18.6 天**。

```json
{"accountNo":"20240001", "userName":"…", "schoolName":"中南林业科技大学",
 "client_id":"flysource_wise_wxapp", "exp":1792302864,
 "detail":{"sysAuthType":"sms","isSysUserSecondAuth":true}}
```

> 注意 `detail.isSysUserSecondAuth: true` —— 该账号启用了短信二次认证。
> 这不影响本系统的自动签到（签到接口不要求二次认证），但会**阻止**
> 用账号密码换取新 token（`grant_type=password` 会走二次认证）。
> 因此本系统采用「用户绑定一次凭据 → 长期复用」的模式，而不是每次重新登录。

若 token 过期，需要重新抓一次包（或改用其它凭据获取方式）。

## 七、签到状态码语义（2026-10-09 修正）

### 事故经过

2026-10-07 与 10-08 两天，系统在 21:11:48 **签到成功**（日志有 `sign_ok`），
但随后的自动重试收到服务端「您今天已完成签到，请勿重复点击！」，
把记录**改写成了 `failed`**。日历看板上因此显示签到失败，
使用者核对小程序后发现**实际是成功的**。

追查时又基于这份被污染的本地数据，得出了"签到一直没成功"的错误结论。

### 根本原因：状态码表读错了

初版 `SIGN_STATUS_NAMES` 是逆向压缩后的 `pages/views/stusign.js` 得来的，
**把 `0` 和 `3` 的含义搞反了**：

| 状态码 | 初版（错） | 实测（对） | 依据 |
|---|---|---|---|
| 0 | ~~未打卡~~ | **正常**（已签到） | `signStatusName` 字段 |
| 3 | ~~未归~~ | **未签** | 同上 |
| 5 | 离校中 | 离校 | 一致 |

`signStatusName` 是服务端随记录一起返回的**权威中文名**，
当初应该直接用它交叉验证，而不是只信逆向结果。

### 正确的判定方式

**是否已签到，看 `signTime` 有没有值，不要看状态码。**

| 日期 | signStatus | signStatusName | signTime | 真实含义 |
|---|---|---|---|---|
| 2026-09-29 | 0 | 正常 | `21:05:19` | 已签到 ✓ |
| 2026-10-01 ~ 06 | 5 | 离校 | （空） | 离校中，免打卡 |
| 2026-10-07 | 0 | 正常 | `21:11:48` | **已签到 ✓** |
| 2026-10-08 | 0 | 正常 | `21:11:48` | **已签到 ✓** |
| 2026-10-09 | 3 | 未签 | （空） | 今天还没签 |

判定优先级（实现见 `app/services.py: already_signed()`）：

1. `signTime` 有值 → 已签到（最可靠，是签到动作留下的时间戳）
2. `signStatusName` 含「正常 / 已签 / 已打卡」→ 已签到
3. 状态码属于免打卡集合（离校 / 请假 / 走读 / 外宿）→ 视为完成

### 连带修复的第二个缺陷

`due_users()` 原先不检查"今天是否已成功"，只要在计划时刻后 5 分钟内就
每次 `tick` 都返回该用户，于是**连续 5 分钟重复提交**。修复后：

- 今天已签到成功的 → 跳过
- 当天尝试次数达 `MAX_SIGN_ATTEMPTS_PER_DAY`（3 次）→ 跳过

另外「可重试失败」不再覆盖已成功的记录（`_record(keep_success=True)`），
避免同样的污染再次发生。

### 实测证据（2026-10-09 核验）

服务端 `getOne` 对已签到日期的**原始返回**：

```json
{
  "signDate": "2026-10-08",
  "signStatus": 0,
  "signStatusName": "正常",
  "signTime": "21:11:48",
  "signType": 0,
  "createTime": "2026-10-08 00:00:03",
  "updateTime": "2026-10-08 21:11:48"
}
```

对照同一天的 `signDate: "2026-10-09"`（尚未签到）：

```json
{
  "signDate": "2026-10-09",
  "signStatus": 3,
  "signStatusName": "未签",
  "signTime": "",
  "signType": -1
}
```

两者差异一目了然：**已签到的记录有 `signTime`，未签的没有。**

### 历史数据修正

`tools/resync_records.py` 以服务端 `getOne` 为准逐日核对并修正：

```
2026-09-30   signStatus=0 name=正常 signTime='21:11:48'   success  [OK]
2026-10-01~06 signStatus=5 name=离校 signTime=''           success  [OK]
2026-10-07   signStatus=0 name=正常 signTime='21:11:48'   failed → success  [修正]
2026-10-08   signStatus=0 name=正常 signTime='21:11:48'   failed → success  [修正]
```

### 回归测试

`tools/test_e2e.py` 第 22、23 组共 13 项，锁死以下行为：

- `signStatus=0` 且有 `signTime` → 判定为已签到
- `signStatus=3`（未签）→ 判定为未签到
- `signStatus=5`（离校）→ 视为已完成
- 同步历史日期时正确产出 `success`
- 「已完成签到」提示被识别为幂等成功，不记失败
- 可重试失败不覆盖已成功记录
- `due_users()` 跳过当天已签到与超限用户

### 教训

1. **服务端自带的中文名字段是最可靠的对照**，逆向结果必须与它交叉验证
2. **本地记录被污染时，不要在其上做二次推理** —— 直接查服务端原始返回
3. **使用者的界面反馈是重要证据** —— 本次正是"小程序显示已打卡成功"
   一句话推翻了错误结论
